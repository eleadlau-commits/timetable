# Confirmed encoding of the supplied Durham campus card

## Result and scope

The photographed card uses **Telepen Numeric (double-density numeric), AIM variant `]B1`, START 1 / STOP 1**. This identifies the supplied card; it does not establish that every Durham card generation uses this encoding.

The actual filename was `credentials/durham-card-reference.jpg.jpeg`. The original image was read directly and left untouched in its ignored directory. No credential value is included here or in source/test fixtures.

## Evidence

1. Automatic and explicitly Numeric decoding with zxing-wasm 3.1.5 returned the same checksum-valid result from the sideways original (90-degree rotation).
2. Windows' installed OCR engine processed four orientations locally. Its reading of the printed barcode number matched the Numeric decoder's payload exactly. No card-number/student-ID/expiry field was substituted.
3. Forced Alpha decoding was also checksum-valid but did not match the printed number. Code 128 and ITF did not decode. Neither digit count nor scanner branding was used to identify the encoding.
4. Independent BWIPP/bwip-js candidates were generated from the privately verified printed value. Read-only Pillow analysis sampled multiple lines and thresholds across the original decoder quadrilateral, normalizing local scale for perspective/printing variation. Only the Numeric candidate matched the entire narrow/wide run sequence, including start, data, checksum and stop. Alpha, Code 128 and ITF candidates had different run counts.
5. Mean photographic width error was about **0.121 narrow modules**, maximum **0.523**, with every run correctly classified into the one-/three-module width classes. This is a normalized pattern match, not pixel-identical photography. Start and stop patterns matched START 1 / STOP 1.
6. The application's writer symbol matched the independent Numeric pattern exactly. Decoder checksum validity plus the independently generated checksum region corroborate the mandatory Telepen modulo-127 checksum. No checksum value is logged.
7. Generated output decoded back to the identical private value and variant. The barcode's actually displayed pixels, captured only in memory, also decoded to that value and variant.

All printed barcode digits are data. The mandatory checksum is a separate symbol generated by the encoder; manual entry must not append/remove a printed digit as a checksum.

### Exact numeric encoding

For the all-digit form on this card, each adjacent digit pair is converted to a data codeword: `codeword = 10 × first_digit + second_digit + 27`. Leading zero pairs remain significant. The observed 14 printed digits therefore represent seven data codewords, rather than 14 ASCII digit codewords.

The checksum codeword is `(127 - (sum(data_codewords) mod 127)) mod 127`, followed by STOP 1. The complete structure is **START 1 → seven numeric-pair codewords → checksum → STOP 1**, with quiet zones outside it. These rules were cross-checked against the installed independent BWIPP encoder implementation; no private codeword/checksum values are recorded.

START 1 / STOP 1 alone does not announce Numeric mode: these framing patterns can also surround an Alpha interpretation. The matching compressed bar pattern and exact printed-number agreement establish Numeric here. Do not replace the framing with START 2 / STOP 2 simply because a decoder describes the payload as Numeric.

## Implementation

- Direct manual entry now uses the confirmed Numeric profile and supports preview/save without a photo. Input remains a string, preserving zeros, and validates numeric digit pairs. One observed 14-digit card is not used to invent a university-wide fixed length.
- Optional photo verification and exact-value behavior for previously verified non-Numeric cards are preserved; other symbologies are not silently converted.
- Camera acquisition, rear/high-resolution preference, focus, rotation, selection and cleanup were preserved: the original already decodes with that pipeline.
- Preview, exact round-trip checks, quiet zones, integer-aligned rendering, full-screen mode, replacement/deletion and persistent saved-card display remain active.
- Browser storage remains development AES-GCM/IndexedDB storage with its documented same-origin security limits; the native driver remains iOS Keychain-backed and requires device testing.
- Vite now blocks HTTP access to `credentials/` and `secrets/`. Git ignore rules alone would not prevent development-server exposure.

## Reproduce locally without logging credentials

Optional investigation tools contain no real values and are excluded from the synthetic test runner. They require Windows OCR, Python/Pillow and the dev-only bwip-js dependency. Those tools are not production dependencies.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/private-card-ocr.ps1 -ImagePath 'C:\Users\jackc\Documents\Durham app\Campus card\credentials\durham-card-reference.jpg.jpeg'
node scripts/verify-private-card.mjs credentials/durham-card-reference.jpg.jpeg
# Requires the local dev server; creates an isolated temporary browser context:
node scripts/check-private-workflow.mjs credentials/durham-card-reference.jpg.jpeg
Remove-Item -LiteralPath credentials/private-ocr-result.json
```

These tools output only match/format/checksum metadata and suppress payloads/raw exceptions. Keep the original image in `credentials/` and never use it as an automated fixture.

## Remaining limits

On resuming the investigation, the completed reports, manual-entry implementation, private verification scripts and directory protections were reviewed and preserved. **26 unit tests, 20 browser tests and the production build passed again.** No private image analysis was unnecessarily repeated, and no scanner or unrelated application files were changed during this verification pass. This working directory has no `.git` repository, so a tracked-file diff was unavailable; the existing `credentials/` ignore rule remains in place for future Git use.

START 1 Telepen symbols can be interpreted as Alpha or compressed Numeric. Other cards may still require verification; this card was identified using its printed-number agreement and full pattern match. The Numeric manual profile makes the intended interpretation explicit.
